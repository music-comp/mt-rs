## 1. Context (just enough)

T0–T2 added five quartal-side analytical surfaces to `mt-rs/crates/mt/src/quartal/`: `duality`, `verification`, `display`, `centrality`, `functional`. Those surfaces are now mathematically symmetric to their quintal counterparts, but they are **invisible to the MCP server** — `ai-music-theory/mcp-server/Cargo.toml` pins `music-comp-mt = "0.5"`, predating all T0/T1/T2 work (which landed on mt-rs 0.6.0).

T3 is the first phase of MCP exposure. Two things happen:

1. **Bump the `music-comp-mt` dependency from 0.5 to 0.6.x** so the new quartal additions are actually accessible in the MCP server.
2. **Add five new MCP tools** that surface the T1/T2 analytical layer (functional grammar + centrality + display) through the MCP protocol with a `q4_*` naming prefix.

The remaining MCP tools — chord-level computation (`q4_fiber_cycle`, `q4_chord_neighbours`, etc.) and verifiers (`verify_q4_universal_l1_law`, `verify_q4_orbits_self_dual`) — will land in T4. The walkthrough phase (originally T4 in PLAN.md) is then renumbered to T5+; the document numbering (`oth4-01` through `oth4-09`) is independent of T-phase numbering and does not change.

### 1.1 Why split MCP exposure across two phases?

T0 → T1 → T2 each added ~150–500 lines and concluded with a clean review. Doing all 10 v2-tooling-spec MCP tools in one phase would be a sudden ~600–1200 line phase — an outlier that breaks the rhythm. Splitting into two phases of ~5 tools each keeps the per-phase discipline that's been working. T3 (this spec) handles the read-only descriptive tools that mirror the T1/T2 analytical layer; T4 will handle chord-level compute and verifier tools.

### 1.2 What's already in place on the MCP side

Significant quartal awareness already exists in `crates/server/src/tools/oth.rs` (1881 lines, 45 tests):

- `parse_orbit_identifier` already accepts both quintal (`Q777`) and quartal (`Q555`) orbit labels.
- The shared `OrbitObject` response struct already includes `quartal_label: String` alongside `quintal_label: String`.
- All 12 existing `oth_*` tools that return orbit info already surface quartal labels.
- Tests already cover quartal-label parsing and quartal_label-in-response.

T3 does **not** modify any of this. It adds new tools alongside existing ones and reuses existing helpers (`parse_orbit_identifier`, `pc_to_note_name`, `OrbitObject`, etc.) where applicable.

### 1.3 What's invisible until the dep bump

Without bumping mt-rs to 0.6, the MCP server cannot use:

- T0: `verify_quartal_universal_l1_law`, `verify_quartal_fiber_classes`, `quartal_reading`, `quintal_reading`, `t_quartal_reversal_equivalence`.
- T1: `render_quartal_chord_dashed`, `render_quartal_is`, `quartal_saddle_chords`, `quartal_orbits_by_betweenness`.
- T2: `QuartalOrbit::functional_region`, `quartal_orbits_in`, `quartal_pathway_stops`, `FunctionalRegion`, `Pathway`.

The dep bump is non-negotiable; everything in T3 (and T4) depends on it.

## 4. Spec — `crates/server/src/tools/q4.rs`

### 4.1 Module-level intent

Quartal-perspective MCP tools that surface the T1/T2 analytical layer of `music-comp-mt::quartal`. Mirrors the organisational shape of `oth.rs` but contains only quartal-perspective tools. No new mathematics — every handler is a thin wrapper around a quartal API call from mt-rs, plus serialization into a JSON-friendly response struct.

Module docstring should reference `crate::tools::oth` as the analogous quintal-perspective home and explain the topical separation: `oth.rs` houses tools whose primary perspective is quintal (with quartal labels included as a courtesy field); `q4.rs` houses tools whose primary perspective is quartal.

### 4.2 Public surface (5 tools)

#### Tool 1 — `q4_functional_region`

**Purpose.** Given a [`FunctionalRegion`] (Summit, Plateau, Slope, Valley, Saddle, Precipice, Narrows), return the quartal orbits in that region with quartal IS labels.

**MCP-level signature:**

```rust
#[derive(Deserialize)]
pub struct Q4FunctionalRegionArgs {
    /// Region name: "Summit", "Plateau", "Slope", "Valley", "Saddle", "Precipice", "Narrows".
    /// Case-insensitive.
    pub region: String,
}

#[derive(Serialize)]
pub struct Q4FunctionalRegionResponse {
    pub region: String,
    pub orbit_count: usize,
    pub quartal_orbits: Vec<Q4OrbitSummary>,
}

#[derive(Serialize)]
pub struct Q4OrbitSummary {
    pub quartal_label: String,    // e.g., "Q555"
    pub quintal_label: String,    // e.g., "Q777"
    pub quartal_is: [u8; 3],      // e.g., [5, 5, 5]
    pub quintal_is: [u8; 3],      // e.g., [7, 7, 7]
    pub size: usize,
    pub degree: usize,
}
```

**Handler.** Calls `parse_region(args.region)` (a new helper), then `quartal_orbits_in(region)`, then maps each `QuartalOrbit` into `Q4OrbitSummary` via a new `build_q4_orbit_summary(orbit)` builder.

**Tool description (for MCP schema):** `"Get all quartal orbits in a given functional region (Summit, Plateau, Slope, Valley, Saddle, Precipice, Narrows). Returns orbits with their quartal and quintal interval structures, sizes, and degrees."`

#### Tool 2 — `q4_pathway`

**Purpose.** Given a canonical `Pathway` (`Cadence` or `Departure`), return the quartal-labelled stop list — region by region, with quartal orbits at each stop.

**MCP-level signature:**

```rust
#[derive(Deserialize)]
pub struct Q4PathwayArgs {
    /// Pathway name: "Cadence" or "Departure". Case-insensitive.
    pub pathway: String,
}

#[derive(Serialize)]
pub struct Q4PathwayResponse {
    pub pathway: String,
    pub stops: Vec<Q4PathwayStop>,
    pub stop_count: usize,
}

#[derive(Serialize)]
pub struct Q4PathwayStop {
    pub region: String,
    pub quartal_orbits: Vec<Q4OrbitSummary>,
}
```

**Handler.** Calls `parse_pathway(args.pathway)`, then `quartal_pathway_stops(pathway)`, then maps each `(FunctionalRegion, Vec<QuartalOrbit>)` into `Q4PathwayStop`.

**Tool description:** `"Get the quartal-labelled stop list for a canonical OTH pathway (Cadence: Saddle → Slope → Summit, or Departure: Summit → Plateau → Slope → Saddle). Each stop pairs the region with its quartal orbits."`

#### Tool 3 — `q4_orbits_by_betweenness`

**Purpose.** Return all 14 quartal orbits ranked by maximum betweenness centrality of any member chord (descending), in quartal vocabulary.

**MCP-level signature:**

```rust
#[derive(Deserialize)]
pub struct Q4OrbitsByBetweennessArgs {} // no input

#[derive(Serialize)]
pub struct Q4OrbitsByBetweennessResponse {
    pub ranking: Vec<Q4OrbitBetweennessEntry>,
}

#[derive(Serialize)]
pub struct Q4OrbitBetweennessEntry {
    pub rank: usize,                    // 1..=14
    pub quartal_label: String,
    pub quintal_label: String,
    pub quartal_is: [u8; 3],
    pub max_betweenness: f64,
    pub functional_region: String,      // e.g., "Saddle"
}
```

**Handler.** Calls `quartal_orbits_by_betweenness(get_space())` and zips with `1..=14` for rank. For each entry, also includes the functional region (via `orbit.functional_region()`).

**Tool description:** `"Rank all 14 quartal orbits by maximum betweenness centrality of any member chord (descending). Returns each orbit's quartal label, quintal label, interval structure, max betweenness, and functional region (e.g., Saddle, Summit)."`

#### Tool 4 — `q4_saddle_chords`

**Purpose.** Return the six saddle chords (top by betweenness centrality) as quartal-perspective chord descriptions, including each chord's quartal interval structure and the quartal-perspective dashed rendering.

**MCP-level signature:**

```rust
#[derive(Deserialize)]
pub struct Q4SaddleChordsArgs {} // no input

#[derive(Serialize)]
pub struct Q4SaddleChordsResponse {
    pub orbit: String,                  // always "Q646" (= quintal Q686)
    pub chords: Vec<Q4ChordSummary>,
}

#[derive(Serialize)]
pub struct Q4ChordSummary {
    pub pcs: Vec<u8>,                   // e.g., [0, 2, 6, 8]
    pub notes: Vec<String>,             // ascending pc → note names ["C", "D", "F#", "G#"]
    pub quartal_is: [u8; 3],            // e.g., [6, 4, 6]
    pub quartal_dashed: String,         // quartal stack walk: "D–G#–C–F#"
    pub quintal_dashed: String,         // quintal stack walk: "C–F#–D–G#"
}
```

**Handler.** Calls `quartal_saddle_chords(get_space())`, maps each `(PcChord, QuartalIntervalStructure)` into a `Q4ChordSummary` via the existing `pc_to_note_name` helper plus calls to `render_quartal_chord_dashed` and `render_chord_dashed`.

**Tool description:** `"Get the six saddle chords (members of the Q646 / Q686 orbit at maximum betweenness centrality) with their quartal interval structures and both quartal and quintal stack-walk renderings."`

#### Tool 5 — `q4_render_chord`

**Purpose.** Given a four-pc chord, return both its quartal and quintal stack-walk renderings, plus quartal IS.

**MCP-level signature:**

```rust
#[derive(Deserialize)]
pub struct Q4RenderChordArgs {
    /// Four pitch classes in 0..=11.
    pub pcs: Vec<u8>,
}

#[derive(Serialize)]
pub struct Q4RenderChordResponse {
    pub pcs: Vec<u8>,
    pub pcset_dashed: String,          // ascending: "C–D–G–A"
    pub quartal_dashed: String,        // quartal walk: "A–D–G–C"
    pub quintal_dashed: String,        // quintal walk: "C–G–D–A"
    pub quartal_is: Option<[u8; 3]>,   // None if chord has no legal IS (out of base space)
    pub quintal_is: Option<[u8; 3]>,   // None if chord has no legal IS
    pub orbit: Option<Q4OrbitSummary>, // None if chord is not in BaseSpace
}
```

**Handler.** Validates `args.pcs.len() == 4`, constructs a `PcChord`, calls `render_pcset_dashed`, `render_quartal_chord_dashed`, `render_chord_dashed` (the existing quintal-side renderer from mt-rs), `pc_chord_quartal_intervals`, `chord.interval_structure()`, and `classify_orbit`. Returns the assembled response with `Option` fields for cases where the chord lies outside the legal base space.

**Tool description:** `"Render a four-pc chord in three forms: ascending pitch-class set, quartal stack walk (using [4,5,6]-legal forward intervals), and quintal stack walk (using [6,7,8]-legal forward intervals). Also returns quartal/quintal interval structures and orbit classification when the chord is in the canonical base space."`

### 4.3 Helper functions (new, in `q4.rs`)

```rust
/// Parse a [`FunctionalRegion`] from a case-insensitive string.
/// Returns `Err(Error::parse(...))` with the list of valid names if unknown.
fn parse_region(s: &str) -> Result<FunctionalRegion>;

/// Parse a [`Pathway`] from a case-insensitive string ("Cadence" or "Departure").
fn parse_pathway(s: &str) -> Result<Pathway>;

/// Build a [`Q4OrbitSummary`] from a [`QuartalOrbit`] reference.
/// Combines quartal IS, quintal IS, size, degree, region.
fn build_q4_orbit_summary(orbit: &QuartalOrbit) -> Q4OrbitSummary;
```

The helper functions live in `q4.rs` private scope (no `pub`); only the tool handler functions and Args/Response structs are public.

### 4.4 Imports and reuse

Reuse the following from `crate::tools::oth` (already `pub`):

- `pc_to_note_name` — existing helper
- (optionally) `parse_chord_pcs` — for tool 5's input validation, if its signature suits

Do **not** re-import `OrbitObject` or `ChordSummary` from `oth.rs` for the Q4 responses. Q4 uses its own `Q4OrbitSummary` and `Q4ChordSummary` because they carry slightly different semantics (quartal-first ordering of fields, additional `quartal_dashed` field, etc.). The discipline is: when fields are quartal-perspective-specific, use a new struct rather than augmenting an existing oth struct.

### 4.5 Implementation notes

- `quartal::quartal_saddle_chords(space)` returns `Vec<(PcChord, QuartalIntervalStructure)>` — pair the IS with the `PcChord` directly; don't recompute.
- The quintal-side renderer needed by tool 4 is `music_comp_mt::quintal::render_chord_dashed` (already accessible). Tool 5 needs both.
- Use `OnceLock`-cached `BaseSpace` (the existing `get_space()` in `oth.rs` is private — the q4 module should add its own `get_space()` or reuse the existing one. **Recommendation: add a private cached `get_space()` in `q4.rs`** to avoid a cross-module pub upgrade.) **Decision D-quartal-T3-001.**
- All five handlers are synchronous (`pub fn name(args: ArgsType) -> Result<ResponseType>`) — match the existing `oth.rs` pattern.
- `#[derive(Deserialize)]` on Args, `#[derive(Serialize)]` on Response. No JSON Schema derives required (the registry uses inline `json!({...})` schemas).

## 5. Spec — `crates/server/src/server.rs` updates

### 5.1 Add `Q4ToolsRegistry`

After `OthToolsRegistry` (around line 352), add a new `Q4ToolsRegistry` struct + `impl ToolRegistry for Q4ToolsRegistry`. The registry follows the same shape: `tools()` returns `Vec<Tool>` via `make_tool(name, description, schema)`; `call(name, args)` matches on tool name and dispatches to handlers in `crate::tools::q4`.

### 5.2 Register `Q4ToolsRegistry` with the server

In the server-construction code (likely `FabrykMcpServer::new(...)` or similar — find the existing call that registers `OthToolsRegistry` and extend it). **Decision D-quartal-T3-002**: register `Q4ToolsRegistry` after `OthToolsRegistry` so dispatch order is deterministic — `oth_*` tools dispatch first, `q4_*` tools second. The two registries do not share tool names, so the order is academic, but the convention should be locked.

### 5.3 Schema specifications for the five tools

Each tool needs an inline `json!({...})` schema in the `tools()` method. Given the MCP server's existing pattern, schemas should:

- Set `"type": "object"`.
- Document each `properties` field with a `"description"` and (where applicable) an `"enum"`.
- List required fields in `"required"`.

Example for `q4_functional_region`:

```rust
make_tool(
    "q4_functional_region",
    "Get all quartal orbits in a given functional region (Summit, Plateau, Slope, Valley, Saddle, Precipice, Narrows). Returns orbits with their quartal and quintal interval structures, sizes, and degrees.",
    json!({
        "type": "object",
        "properties": {
            "region": {
                "type": "string",
                "enum": ["Summit", "Plateau", "Slope", "Valley", "Saddle", "Precipice", "Narrows"],
                "description": "Functional region name (case-insensitive)."
            }
        },
        "required": ["region"]
    }),
),
```

Schemas for the other four follow the same pattern — see §4.2 for required fields.

### 5.4 Do not modify

- The existing `MusicTheoryToolsRegistry` (9 tools).
- The existing `OthToolsRegistry` (12 tools, 45 inline tests in `oth.rs`).
- Any handler in `crates/server/src/tools/oth.rs`.
- Any existing tests.

## 10. Style Notes (T3 conventions)

- Tool handler functions are `pub fn name(args: ArgsType) -> Result<ResponseType>` (synchronous, matches `oth.rs`).
- Args structs derive `Deserialize`. Response structs derive `Serialize, Clone`.
- Field naming in JSON output follows the existing `oth.rs` convention (`snake_case`).
- Tests use `test_<fn>_<scenario>` naming (project CLAUDE.md convention).
- Error reporting uses `Error::parse(format!(...))` for input-validation failures, matching existing patterns.
- `#[must_use]` on response struct types where natural; not required on tool handler functions (they're called by the MCP dispatch layer, not by user code that could ignore the result).
- Doctests on public response struct types are nice-to-have but not required (they're often not naturally doctestable — the response shape is the documentation).
- Asymmetric-coverage discipline (T0/T1/T2 lesson): at least one test per tool that operates on chord/orbit data must use an asymmetric orbit (Q554) or a chord from such an orbit. Already baked into §6.1.

## 13. T0–T2 Lessons Already Applied

For convenient reference — these are baked in:

- **`#[must_use]` on every new public function/struct where natural.** Tool handlers are an exception (per §10 above); response structs use it.
- **Asymmetric-coverage discipline.** §6.1 includes `test_q4_render_chord_q554_asymmetric` — explicit regression test against pcs `[0,3,8,10]` checking quartal IS `(5,5,4)`, distinct from the palindromic Q555/Q646 cases.
- **Speculative-struct deferral.** No `Q4PathwayDetail` with chord enumerations — walkthrough drives any such design.
- **Topical-submodule organization.** New `q4.rs` mirrors mt-rs's quartal/ topical-submodule convention.
- **Cite live baselines.** §7 acceptance gates on "baseline + N", not on absolute counts (the MCP server's baseline differs from mt-rs's and this spec doesn't have visibility into the exact pre-T3 count — that's CC's first task at implementation time).
- **Plan-doc-to-main convention** (locked at end of T2): the T3 plan document, when CC produces it, should land on `main` of `ai-music-theory` *before* the impl branch starts work, or be cherry-picked to `main` first if produced in one continuous session.
- **CLAUDE.md cleanup is out of scope by default**, except where a one-paragraph addition is symmetric with the mt-rs CLAUDE.md update (optional; D-quartal-T3-003).
- **No CLAUDE.md edits coupled to T-phase work.** Same rule, different repo.
