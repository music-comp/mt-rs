# Phase 3.5: Quartal Module

## Design Analysis: What Is the Quartal Module, Really?

Before writing a single line of code, we need to confront the central question: **what does a quartal module add that the quintal module doesn't already provide?**

The duality theorem (paper §26) proves that quartal and quintal are *orientation reversal on the same fiber*. The base space B is identical — it's the same 228 chords, the same adjacency graph, the same geodesics, the same orbits, the same centrality. The extended space E is the same fibers. The only difference is traversal direction: t₁ (quintal, ascending fifths) vs t₋₁ (quartal, descending fourths, equivalently ascending fourths).

This means the quartal module is NOT a parallel implementation. It is a **reframing layer** that:

1. **Provides quartal-native vocabulary** — intervals described as fourths (P4=5, A4=6, d4=4) rather than fifths, with a [4,6] constraint that is the complement of [6,8]
2. **Reverses the default traversal direction** — t₋₁ is the primary operator, t₁ is the reverse
3. **Relabels inversions** — what quintal calls "1st inversion" quartal calls "3rd inversion" (and vice versa)
4. **Provides quartal-idiomatic constructors** — building chords from stacked fourths rather than stacked fifths
5. **Shares ALL the heavy computation** — the same `BaseSpace`, orbits, geodesics, centrality

The architecture should reflect this: the quartal module is thin, delegates to quintal internals, and adds a quartal-specific API surface.

---

## Architecture Decision: Shared Core + Dual Facades

### Option A: Quartal as a wrapper around Quintal (rejected)
`quartal::BaseSpace` wraps `quintal::BaseSpace`. Problems: awkward ownership, every quartal method needs to unwrap/rewrap, testing is indirect.

### Option B: Extract shared core, two sibling facades (recommended)
Extract the interval-constraint-agnostic logic into a shared internal module, then have both `quintal` and `quartal` as thin facades over it.

But wait — the [6,8] constraint and the [4,6] constraint produce the *same 228 chords*. A four-note pc set with consecutive intervals in {6,7,8} (reading bottom-up as fifths) is exactly the same set read top-down as fourths with consecutive intervals in {4,5,6}. They are literally the same set of pitch classes.

This means we don't need to re-enumerate anything. The quartal module needs:

### Option C: Quartal as a sibling that re-exports and reframes (recommended)
- `quartal/mod.rs` — public API with quartal-native types and vocabulary
- `quartal/types.rs` — thin quartal-specific types that wrap or re-export quintal types with quartal semantics
- `quartal/interval.rs` — the [4,6] interval constraint and quartal interval vocabulary
- `quartal/voicing.rs` — quartal-native constructors (stacked fourths) and the t₋₁-primary traversal
- `quartal/conversion.rs` — explicit conversion between quartal and quintal perspectives on the same underlying data

The key insight: **the quartal module doesn't recompute the base space. It shares it.** The `BaseSpace`, orbits, geodesics, centrality — all of these are reused directly from `quintal`. The quartal module provides quartal-native *entry points* and *interpretation*.

## Phase 3.5 Structure: 3 Milestones

### Milestone 3.5.1: Quartal Types & Interval Vocabulary

**Scope:** Define quartal-specific types, the [4,6] interval constraint, and quartal-native constructors.

**Deliverables:**

- `quartal/mod.rs` — module root
- `quartal/types.rs`:
  - `QuartalInterval` — enum or wrapper for {d4=4, P4=5, A4=6}, the quartal complement of {d5=6, P5=7, A5=8}
  - `QuartalIntervalStructure` — 3-tuple of quartal intervals, representing a chord read top-to-bottom
  - `QuartalVoicedChord` — a voiced chord with quartal semantics: voices in *descending* order (highest first), or equivalently ascending fourths from top. This is a newtype over `VoicedChord` with quartal-native methods.
  - Document and implement the bijection: quintal interval i maps to quartal interval (12 − i) mod 12. So P5=7 ↔ P4=5, d5=6 ↔ A4=6, A5=8 ↔ d4=4. Note the tritone (6) is its own dual!
  
- `quartal/interval.rs`:
  - `is_quartal_legal(intervals: &QuartalIntervalStructure) -> bool` — each interval ∈ {4, 5, 6}
  - `quintal_to_quartal_interval(semitones: u8) -> u8` — `(12 - semitones) % 12`
  - `quartal_to_quintal_interval(semitones: u8) -> u8` — same function (it's an involution!)
  - `quintal_to_quartal_structure(qs: &IntervalStructure) -> QuartalIntervalStructure` — reverses and complements: (i₁,i₂,i₃) → (12−i₃, 12−i₂, 12−i₁)
  - `quartal_to_quintal_structure(qs: &QuartalIntervalStructure) -> IntervalStructure` — inverse (same operation, it's an involution)

- `quartal/conversion.rs`:
  - `to_quartal(chord: &VoicedChord) -> QuartalVoicedChord` — reinterpret a quintal voiced chord as quartal (reverse voice order)
  - `to_quintal(chord: &QuartalVoicedChord) -> VoicedChord` — reverse
  - `pc_chord_quartal_intervals(chord: &PcChord) -> QuartalIntervalStructure` — read a pc chord's intervals top-to-bottom as quartal intervals

**Mathematical context for CC:**

> **Quartal/Quintal interval duality:** Every interval has a complement mod 12. The perfect fifth (7 semitones) complements the perfect fourth (5 semitones): 7 + 5 = 12. The augmented fifth (8) complements the diminished fourth (4): 8 + 4 = 12. The tritone (6) is self-complementary: 6 + 6 = 12.
>
> **Reading direction:** A quintal chord C-G-D-A read bottom-to-top has intervals (7,7,7) — three perfect fifths. The same chord read top-to-bottom has intervals (5,5,5) — three perfect fourths. These are the same pitch classes, the same chord, but described in two dual vocabularies.
>
> **The [4,6] constraint:** The quartal analogue of the [6,8] quintal constraint. An interval is "quartal-legal" if it is 4, 5, or 6 semitones — a diminished fourth, perfect fourth, or augmented fourth (= tritone). This is exactly the complement of [6,8]: for each quintal interval i ∈ {6,7,8}, the quartal complement (12−i) ∈ {6,5,4} = {4,5,6}.
>
> **Interval structure reversal:** If a pc chord has quintal interval structure (i₁,i₂,i₃) reading bottom-to-top, its quartal interval structure reading top-to-bottom is (12−i₃, 12−i₂, 12−i₁). The reversal reflects the change in reading direction; the complementation reflects the change from fifths to fourths.

**Tests:**

- Complement bijection: `quintal_to_quartal_interval(7) == 5`, `quintal_to_quartal_interval(6) == 6`, `quintal_to_quartal_interval(8) == 4`
- Involution: `quintal_to_quartal_interval(quartal_to_quintal_interval(x)) == x` for all x in {4,5,6}
- Structure conversion: quintal (7,7,7) → quartal (5,5,5); quintal (6,8,6) → quartal (6,4,6)
- Structure round-trip: converting quintal → quartal → quintal recovers the original
- `is_quartal_legal` accepts {4,5,6} combinations, rejects {3,7,8,...}
- Every one of the 228 chords satisfies both the quintal [6,8] AND the quartal [4,6] constraint (when read in the appropriate direction) — this is a key structural verification
- `QuartalVoicedChord` from C3-G3-D4-A4 has quartal reading (5,5,5) when read top-to-bottom

**Estimated session size:** ~300 lines of Rust + ~250 lines of tests

### Milestone 3.5.2: Quartal Traversal & Fiber Access

**Scope:** Quartal-primary inversion traversal (t₋₁ as the "forward" direction), quartal orbit labels, quartal-native access to the shared base space.

**Deliverables:**

- `quartal/voicing.rs`:
  - `quartal_inversion_cycle(chord: &QuartalVoicedChord) -> [QuartalVoicedChord; 4]` — the inversion cycle traversed via t₋₁ (quartal "forward"). This visits the same 4 chords as the quintal cycle, but in reverse order: [inv₀, inv₃, inv₂, inv₁] in quintal labeling, which quartal labels as [inv₀, inv₁, inv₂, inv₃].
  - `t_quartal(chord: &QuartalVoicedChord) -> QuartalVoicedChord` — one step in the quartal direction (= t₋₁ in quintal terms). Each voice moves DOWN to the previous chord-scale degree.
  - `t_quartal_reverse(chord: &QuartalVoicedChord) -> QuartalVoicedChord` — one step in the reverse-quartal direction (= t₁ in quintal terms)
  - `quartal_l1_distances(chord: &QuartalVoicedChord) -> [u32; 4]` — L1 distances between consecutive quartal inversions. Must be [12,12,12,36] — the Universal L1 Law holds in both directions.

- `quartal/orbit.rs`:
  - `QuartalOrbit` — enum mirroring the 14 orbit types but with quartal interval labels. The quintal [P5,P5,P5] orbit (intervals 7,7,7) is the quartal [P4,P4,P4] orbit (intervals 5,5,5). The orbits with asymmetric interval sequences get reversed labels: quintal [P5,P5,d5] (7,7,6) becomes quartal [A4,P4,P4] (6,5,5).
  - `quartal_orbit_label(orbit: &Orbit) -> QuartalOrbit` — convert quintal orbit to quartal labeling
  - `quartal_analogies()` — the 4 "named" orbits in quartal vocabulary: [P4,P4,P4] = major analogue, [P4,d4,P4] = minor analogue, [A4,d4,A4] = augmented analogue, [A4,P4,A4] = diminished analogue

- Re-exports from `quintal` (documented as shared):
  - `BaseSpace` — re-exported as-is (the graph is identical)
  - `PcChord` — re-exported (pitch-class sets are orientation-independent)
  - All geodesic, distance, centrality functions — re-exported

**Mathematical context for CC:**

> **Quartal traversal = t₋₁:** The quartal "forward" inversion operator moves each voice DOWN to the previous chord-scale degree. This is t₋₁ in the quintal convention, and it traverses the fiber in reverse order.
>
> **Quartal inversion labeling:** If quintal labels the fiber [inv₀, inv₁, inv₂, inv₃] via t₁, quartal labels the same fiber [inv₀, inv₃, inv₂, inv₁] via t₋₁. So quintal's "1st inversion" is quartal's "3rd inversion" and vice versa. The root position (inv₀) is the same in both — it's the unique [6,8]-legal member (for Class A orbits).
>
> **Quartal orbit naming:** Each quintal interval structure (i₁,i₂,i₃) has a quartal dual (12−i₃, 12−i₂, 12−i₁). For the 8 asymmetric orbits, this reversal+complementation gives a different interval tuple (though the same T/I orbit). The 6 symmetric orbits (palindromic interval sequences under complement) have identical quintal and quartal labels: e.g., [d5,A5,d5] = (6,8,6) → quartal (6,4,6) = [A4,d4,A4]. Wait — that's actually different! Let me verify...
>
> Actually: quintal (6,8,6) bottom-to-top. Quartal reads top-to-bottom: the intervals reverse to (6,8,6), then complement each to (6,4,6). So quintal [d5,A5,d5] becomes quartal [A4,d4,A4]. These ARE different labels for the same orbit. The orbit is self-dual (both labels refer to the same 6 chords), but the quartal name differs from the quintal name.
>
> **All 14 T/I orbits are self-dual** (proved in paper §26): every orbit contains both its quintal representative and its quartal dual. The 6 "asymmetric" quintal/quartal pairs collapse under inversion Iₙ, which is why we get 14 T/I orbits from 20 T-only orbits.

**Tests:**

- **Duality verification (the critical tests):**
  - `quartal_inversion_cycle` for C3-G3-D4-A4 visits the same 4 voiced chords as `quintal::inversion_cycle`, but in reverse order
  - For every chord in B: quartal cycle set == quintal cycle set (as unordered sets)
  - Quartal L1 distances are [12,12,12,36] for ALL 228 chords (Universal L1 Law holds in both directions)
  - `t_quartal(t_quartal_reverse(chord))` recovers the original chord's pc set
  - `t_quartal` composed 4 times = T₋₁₂ (transposition down one octave)
  
- **Orbit labeling:**
  - All 14 QuartalOrbits are populated
  - Each QuartalOrbit maps to exactly one quintal Orbit (bijection)
  - Quartal [P4,P4,P4] has orbit size 12, degree 8 (same as quintal [P5,P5,P5])
  - The 4 quartal analogies map to the 4 quintal analogies (major↔major, etc.)
  - Orbit sizes are preserved under relabeling (they must be — same chords!)

- **Round-trip consistency:**
  - `to_quartal(to_quintal(qc))` recovers the original quartal chord
  - `quartal_orbit_label(quintal_orbit)` → `quintal_orbit_from_quartal(quartal_orbit)` round-trips

- **Re-export verification:**
  - `quartal::BaseSpace` is the same type as `quintal::BaseSpace`
  - Distance, geodesic, centrality functions produce identical results when called through quartal vs quintal paths

**Estimated session size:** ~350 lines of Rust + ~350 lines of tests

### Milestone 3.5.3: Quartal-Native Constructors & Integration Tests

**Scope:** Idiomatic quartal chord construction, comprehensive cross-module integration tests, and documentation.

**Deliverables:**

- `quartal/constructors.rs`:
  - `from_stacked_fourths(root_pc: u8, intervals: &[u8]) -> Result<PcChord, QuartalError>` — build a chord by stacking fourths (ascending) from a root pitch class. Validates that each interval ∈ {4,5,6}. E.g., `from_stacked_fourths(9, &[5,5,5])` builds A-D-G-C = {9,2,7,0} = the quartal reading of C-G-D-A.
  - `from_stacked_fourths_voiced(root_pitch: u8, intervals: &[u8]) -> Result<QuartalVoicedChord, QuartalError>` — voiced version, building upward from a root MIDI pitch in fourths
  - `pure_quartal_stack(root_pc: u8) -> PcChord` — convenience for three perfect fourths: `from_stacked_fourths(root, &[5,5,5])`
  - `quartal_neighbors(chord: &PcChord, space: &BaseSpace) -> Vec<PcChord>` — adjacent chords, presented with quartal interval structures

- `quartal/error.rs`:
  - `QuartalError` — error enum for quartal-specific validation failures

- Integration tests (`tests/quartal/`):
  - `test_quartal_quintal_identity.rs` — exhaustive tests proving quartal and quintal produce identical mathematical results:
    - For every one of the 228 chords: verify the quintal interval structure (i₁,i₂,i₃) and quartal interval structure (12−i₃, 12−i₂, 12−i₁) describe the same chord
    - For every orbit: verify the quintal orbit and quartal orbit contain the same chords
    - For every fiber: verify the quartal and quintal cycles visit the same 4 voiced chords
    - For every saddle chord: verify it has degree 8, maximum betweenness, and 2 inversions in [6,8] from both the quartal and quintal perspective
  
  - `test_quartal_constructors.rs`:
    - `pure_quartal_stack(0)` = {0,5,10,3} = C-F-B♭-E♭ — a stack of three P4s from C
    - Verify that `pure_quartal_stack(0)` and quintal's pure stack starting from E♭ (= `pure_quintal_stack(3)`) describe the same pc set {0,3,5,10} (just sorted differently)
    - `from_stacked_fourths` with invalid intervals (e.g., [3,5,5]) returns error
    - `from_stacked_fourths_voiced` builds ascending fourths: A2-D3-G3-C4 with quartal intervals (5,5,5)
    - Every chord built via quartal constructors is in the shared BaseSpace

  - `test_persichetti_examples.rs` — verify examples from Persichetti's "Twentieth-Century Harmony" (the Persichetti concept cards provide concrete quartal voicings):
    - Three-note quartal chords (P4+P4, P4+A4, A4+P4) are subsets of our four-note space
    - Four-note quartal chords match our pure quartal stacks
    - "Chord identity remains quartal; only the voicing changes" — verify computationally

**Mathematical context for CC:**

> **Quartal stacking direction:** Quartal chords are conventionally described as stacking fourths *upward*: C-F-B♭-E♭ is "C with three perfect fourths stacked above." This is the reverse of the quintal convention (stacking fifths upward: C-G-D-A). The crucial point: C-F-B♭-E♭ and E♭-B♭-F-C are the same pitch-class set {0,3,5,10}. The quartal module's constructors should build upward in fourths (matching the conventional description), but the underlying PcChord is orientation-independent.
>
> **Quartal root vs quintal root:** A quartal stack C-F-B♭-E♭ has quartal root C (bottom of the fourth-stack). The same chord read as a quintal stack would be E♭-B♭-F-C with quintal root E♭. The pc set {0,3,5,10} is the same either way. The "root" is a property of the reading convention, not of the chord itself. The quartal module should track quartal root; the quintal module tracks quintal root. Neither is more fundamental.
>
> **Persichetti's observation:** "Quartal chords are extremely useful in their inverted forms." This is computationally verified by our framework: the inversion cycle of any quartal chord (traversed via t₋₁) produces voicings with different acoustic character but identical pitch-class content. For Class B orbits, 2 of 4 inversions remain in [4,6] (quartal-legal), giving the composer two quartal-sounding voicings of the same chord.

**Tests (continued):**

- **Quartal root tracking:**
  - `pure_quartal_stack(0)` has quartal root 0 (C)
  - The same chord viewed as quintal has quintal root 3 (E♭)
  - Quartal root + quintal root together fully characterize the orientation

- **Error handling:**
  - `from_stacked_fourths(0, &[5,5,5,5])` fails (too many intervals — we want 4-note chords, so 3 intervals)
  - `from_stacked_fourths(0, &[5,5])` fails (too few intervals)
  - `from_stacked_fourths(0, &[3,5,5])` fails (3 is not in {4,5,6})
  - `from_stacked_fourths(0, &[5,5,7])` fails (7 is not in {4,5,6})

- **Cross-module consistency (the most important tests):**
  - `quartal::BaseSpace` and `quintal::BaseSpace` contain the same 228 chords
  - Distance between any two chords is identical whether computed via quartal or quintal
  - All 6 saddle chords are identified as saddle from both perspectives

**Estimated session size:** ~300 lines of Rust + ~400 lines of tests

## Refactoring Consideration

After Phase 3.5 is complete, there's a natural follow-up refactor opportunity: extract the truly shared infrastructure (BaseSpace, graph algorithms, orbit classification) into a private `common` or `interval_space` sub-module that both `quintal` and `quartal` depend on, rather than having `quartal` depend on `quintal` pub types. This would be a clean internal restructuring with no API changes. I'd recommend deferring this to a separate session — get the quartal module working first, then clean up the dependency direction.

## Dependency on Quintal Module

The quartal module depends on the following quintal public API:

**Types (re-exported or wrapped):**
- `PcChord`, `VoicedChord`, `IntervalStructure`
- `Orbit`, `FiberClass`
- `BaseSpace`

**Functions (called internally):**
- `quintal::base_space::enumerate_all()`
- `quintal::fiber::t1()`, `quintal::fiber::t_minus1()`
- `quintal::fiber::inversion_cycle()`, `quintal::fiber::chord_scale()`
- `quintal::fiber::l1_distance()`
- `quintal::orbit::classify_orbit()`
- `quintal::distance::*`, `quintal::geodesics::*`, `quintal::centrality::*`

The quartal module should NOT duplicate any of this logic. It wraps, relabels, and re-exports.
