# Phase 2.1 + 2.2 + 2.3 Dev Plan

## Context

Phase 1 landed `harmonize_melody` (commit `7c89f63`). This bundle takes the reference sketch from "compiles and tests pass" to "production-quality public API." Three sub-phases are bundled because they share file boundaries: changing `target_midi` to `i16` (2.2) breaks test assertions written against `u8` (2.1/2.3), and tightening visibility (2.3) requires restructuring the tests that reach into internals (2.1's `test_candidates.rs` and `test_canonicalize.rs`).

Locked constraints from `0008-phase-2-open-questions-resolved.md`:
- #1: No crate-root re-exports. Access via `music_comp_mt::harmonize::*`.
- #2: `TargetMidiOutOfRange.target_midi` field is `i16`.
- #6: No builder for `HarmonizeOptions`. Document struct-update idiom.

**File:** `crates/mt/tests/harmonize/test_candidates.rs` (lines 86–105)

**After:**

```rust
#[test]
fn test_specific_chord_cgda() {
    let space = BaseSpace::new();
    let candidates = candidates_for_top(60, DualityScope::QuintalOnly, &space, 0).unwrap();
    let cgda = candidates
        .iter()
        .find(|c| {
            let pcs: BTreeSet<u8> = c.pitches.iter().map(|&p| p % 12).collect();
            pcs == [0, 2, 7, 9].iter().copied().collect()

        .expect("CGDA must be in quintal candidates for top=60");
    eprintln!("CGDA candidate with top=60: {:?}", cgda.pitches);
    assert_eq!(cgda.pitches[3], 60);
}
```

### 2.1.2 — `test_shift_overflow` renamed with explicit invariant assertion

**File:** `crates/mt/src/harmonize/candidates.rs` (lines 125–167 in the `#[cfg(test)]` block)

**Before:** 40-line rambling comment body that concludes "overflow is impossible" with only an identity-shift assertion.

**After:** Rename to `test_overflow_unreachable_for_u8_target` with a concise assertion. **Use a target that PC-matches the chord's top voice** — `shift_to_top` has a `debug_assert!(delta % 12 == 0)` precondition, so passing a PC-mismatching target panics in debug mode rather than returning a useful result.

```rust
#[test]
fn test_overflow_unreachable_for_u8_target() {
    // For any ascending VoicedChord and any target_midi: u8 (≤ 127),
    // top_after = target_midi ≤ 127, and bottom_after < top_after
    // (because pitches are strictly ascending). So bottom_after ≤ 127.
    // Overflow is structurally impossible — verified here at the upper
    // boundary. Underflow handling is verified by `test_shift_underflow`.
    let c = VoicedChord::new([48, 55, 62, 69]).unwrap();
    // c.pitches[3] = 69, PC 9. Highest PC-9 MIDI ≤ 127 is 117.
    // delta = +48; bottom = 96, top = 117. Both in [0, 127].
    assert!(shift_to_top(&c, 117, 0).is_ok());
}
```

(Do NOT add an underflow assertion here. PC-mismatch targets violate `shift_to_top`'s precondition and panic in debug; PC-matching low targets duplicate `test_shift_underflow`'s coverage. Keep this test focused on its name.)

**Ref:** Phase 2 plan §2.1 deliverable 2.

### 2.2.7 — Per-variant rustdoc paragraphs on `HarmonizeError`

**File:** `crates/mt/src/harmonize/mod.rs`

Add doc comments above each variant:

```rust
/// Errors returned by [`harmonize_melody`].
#[derive(Debug, thiserror::Error)]
#[non_exhaustive]
pub enum HarmonizeError {
    /// The input melody was empty. At least one note is required.
    #[error("melody must contain at least one note")]
    EmptyMelody,

    /// A pitch class in [`MelodyInput::PitchClasses`] was outside `0..=11`.
    #[error("melody pitch class {0} is outside the valid range 0..=11")]
    InvalidPitchClass(u8),

    /// The computed target MIDI pitch (melody note + `top_voice_offset`) fell
    /// outside the playable range `0..=127`. The `target_midi` field contains
    /// the actual computed value (which may be negative or above 127).
    #[error(
        "target MIDI pitch {target_midi} at position {position} is out of \
         the playable range after applying top_voice_offset"
    )]
    TargetMidiOutOfRange { position: usize, target_midi: i16 },

    /// No candidate chord exists for the target pitch class at the given
    /// position. This should be unreachable for any legal pitch class in
    /// `0..=11` — every PC is contained in at least 76 of the 228 base-space
    /// chords.
    #[error(
        "no candidate chord found for melody position {position} \
         (top pitch {top_midi})"
    )]
    NoCandidatesForPosition { position: usize, top_midi: u8 },
}
```

## Uncertainties / Observations

1. **No bugs found.** The code is correct as written; Phase 2.1–2.3 are pure cleanup/hardening.
2. **The `test_candidates.rs` and `test_canonicalize.rs` files currently import `theory::harmonize::canonicalize::canonicalize_melody` and `theory::harmonize::candidates::candidates_for_top` directly.** These paths break the moment visibility is tightened. The sequencing handles this (move tests first in 2.3.2, then tighten in 2.3.1).
3. **`HarmonizeError` does not derive `PartialEq`/`Eq`** (it uses `thiserror::Error` which doesn't require them). The Display test uses `.to_string()` comparison, not pattern matching. This is fine.
4. **The `position_field_carries_correct_index` test (2.1.5) uses `canonicalize_melody` directly**, which will be `pub(crate)` after 2.3.1. It moves into the in-module test block during 2.3.2 — but for Phase 2.1's commit it lives in `test_canonicalize.rs` temporarily. This is acceptable: the file will be deleted in the same PR (Phase 2.3 commit).
